# Ava Hotel — Voice Concierge → Operations\n\nA compact, production-shaped demo of a **voice AI concierge that does more than answer questions**: it turns a guest conversation into structured operational work.\n\n**Live demo:** https://ava-hotel.vercel.app/  \n**Operations board:** https://ava-hotel.vercel.app/operations\n\n> **Demo property only.** Ava Hotel, guest names, rooms, and staff in this repository are fictional. Do not use real guest PII in the public portfolio deployment.\n\n## Why this exists\n\nMost voice demos stop at conversation. This project demonstrates the harder part: reliably moving from natural language to an operational workflow with validation, idempotency, routing, status transitions, and a staff-facing queue.\n\n```mermaid\nflowchart LR\n  Guest[Guest speaks] --> Vapi[Vapi voice agent]\n  Vapi --> Tool[/Protected Vapi tool/]\n  Tool --> Validate[Validate + route + idempotency]\n  Validate --> DB[(Supabase)]\n  DB --> Feed[/Sanitized operations feed/]\n  Feed --> Board[Operations board]\n  Staff[Staff / supervisor] --> Actions[/Protected action endpoint/]\n  Actions --> DB\n```\n\n## What the demo shows\n\n- **Voice → action:** guest requests become structured service requests.\n- **Workflow routing:** housekeeping, maintenance, and guest-services requests route to the right team.\n- **Idempotency:** repeated tool calls do not create duplicate requests.\n- **Mid-call updates:** a guest can change a request (for example, 3 towels → 2) without creating a second task.\n- **Operational state machine:** `NEW → ASSIGNED → IN_PROGRESS → BLOCKED / COMPLETED`.\n- **SLA awareness:** requests can surface as on-track, at-risk, or breached.\n- **Staff view:** assigned work becomes a simple execution view.\n- **Safe public defaults:** private credentials stay server-side and public manual writes are off by default.\n- **Responsive UI:** five-lane desktop board, horizontal Kanban on narrower screens, stacked lanes on mobile.\n\n## Repository structure\n\n```text\n.\n├── index.html\n├── operations/\n│   ├── index.html\n│   ├── styles.css\n│   └── app.js\n├── vercel.json\n```\n\n## Security model\n\nPrivate credentials never belong in source control.\n\n**Server-only environment variables**\n\n- `SUPABASE_URL`\n- `SUPABASE_SECRET_KEY`\n- `VAPI_TOOL_SECRET`\n- `OPS_ACTION_SECRET`\n\n**Browser-visible by design**\n\n- `VAPI_PUBLIC_KEY`\n- `VAPI_ASSISTANT_ID`\n\nThe Vapi browser identifiers are delivered by `/api/public-config` instead of being hard-coded in the repository. They are not private secrets, but they are account-specific identifiers, so restrict the public key to your production origin and intended assistant.\n\n**Public board defaults**\n\n- Supabase RLS is enabled and anonymous table reads are revoked.\n- `/api/operations-feed` omits guest names, call IDs, idempotency keys, event metadata, and event actor IDs.\n- `/api/request-action` requires `OPS_ACTION_SECRET` unless you intentionally set `DEMO_ALLOW_PUBLIC_WRITES=true`.\n- `DEMO_ALLOW_PUBLIC_WRITES=false` is the recommended public-deployment setting.\n- Same-origin checks are not authentication; the public-write switch is for disposable demo data only.\n\nFor a real hotel deployment, put the operations board behind staff authentication and never expose live guest operations through a public portfolio route.\n\n## Quick start\n\n1. Fork or clone this repository.\n2. Create a Supabase project and run `sql/schema.sql`.\n3. Import the repository into Vercel.\n4. Copy `.env.example` values into **Vercel → Project → Settings → Environments**.\n5. Create a Vapi assistant and add the tool functions below.\n6. Point the Vapi tool server to `https://YOUR_DOMAIN/api/vapi-tool`.\n7. Create a Vapi Custom Credential using **Bearer Token** auth with the same value as `VAPI_TOOL_SECRET`.\n8. Restrict the Vapi public key to your deployment origin and assistant.\n9. Redeploy.\n\n## Vapi tool contract\n\nThe server accepts:\n\n- `create_service_request` — create amenity, housekeeping, late-checkout, or other service work.\n- `create_maintenance_request` — create a maintenance request.\n- `update_service_request` — change an existing request during the same conversation.\n\nExample create payload:\n\n```json\n{\n  "room_number": "512",\n  "guest_name": "Optional",\n  "request_type": "amenity",\n  "details": "2 extra towels",\n  "quantity": 2\n}\n```\n\nSupported `request_type` values: `amenity`, `housekeeping`, `maintenance`, `late_checkout_request`, `other`.\n\nExample update payload:\n\n```json\n{\n  "request_id": "REQ-1042",\n  "quantity": 2,\n  "details": "2 extra towels"\n}\n```\n\n## Reusing the project\n\nThe frontend is deliberately framework-light (HTML/CSS/JS), with Vercel Functions as the server boundary and Supabase for persistence.\n\nTo adapt it:\n\n1. Replace the hotel branding and demo copy.\n2. Change `ROUTING` in `api/vapi-tool.js` for your workflows and SLAs.\n3. Extend the state machine if your operations need more statuses.\n4. Replace the public board with authenticated staff access before using real data.\n5. Add automated tests around tool payload validation, idempotency, and state transitions before production use.\n\n## License\n\nMIT — fork it, adapt it, and use it as a starting point for your own voice-to-workflow prototype.\n
